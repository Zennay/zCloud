# Scheduled redispatch source guard — 16 October 2026

This **GitHub-hosted, read-only** control is independently owned deploy-ops work for [#633](https://github.com/Zennay/zCloud/issues/633), informed by the existing production recovery issue [#1216](https://github.com/Zennay/zCloud/issues/1216). It does not alter the live recovery workflow, schedule, or queue.

## What the check enforces

The workflow has **no PR path filter**: **every main-targeting pull request** starts the source-only check, including PRs retargeted to main via the `edited` event. Fork-origin pull requests fail explicitly in a pre-check on a GitHub-hosted runner (rather than silently yielding a skipped/success check); the untrusted fork is never checked out. A path-filtered guard would miss a newly added risky workflow. For same-repository PRs, the gate checks exact candidate head and canonical live main ref before and after validation, rejecting stale base evidence.

The scanner inventories regular `.github/workflows/*.yml`/`.yaml`, `.github/actions/**/action.yml`/`action.yaml`, and bounded UTF-8 `.github/actions/**` script entrypoint blobs (`.js`, `.mjs`, `.cjs`, `.py`, `.sh`) at immutable Git tree IDs for base and candidate. For workflows with a scheduled event (including inline, quoted and opaque alias-shaped triggers), it identifies direct `gh workflow run`, REST workflow dispatch, REST `repository_dispatch`, Octokit dispatch and dynamic workflow-ID variants. It also recognises the split Python REST URL used by the existing recovery workflow, compact `on: [schedule]` event lists, and GitHub CLI `-R`/`--repo` flags. Scheduled callers are traversed into their **local reusable workflow and composite-action dependency graph**, including nested actions and cyclic graphs (visited once). Action-manifest `runs.main`, `runs.pre` and `runs.post` entrypoint scripts are also inventoried and scanned for direct dispatch patterns. Relative entrypoint paths cannot escape the action directory. New remote reusable workflow references are treated as opaque source risk rather than executed. Quoted YAML keys (`'uses'`, `"uses"`, `'main'`, `"main"`, `'pre'`, `"post"`) are treated as ordinary keys: they cannot hide a local reusable-workflow edge, local composite-action edge, or Node/Python/shell action lifecycle entrypoint. Newly introduced alias/tag or expression-valued `uses:` references within scheduled workflow/action ancestry are conservatively fingerprinted as **opaque action edges**. They are refused pending review rather than evaluated or assumed safe; unchanged legacy opaque edges are grandfathered, and unrelated manually triggered workflows remain outside this scheduled-only gate. Flow-style YAML maps (for example `jobs: { call: { uses: ... } }`, `steps: [{uses: ...}]` and `runs: {using: node20, main: ...}`) are now traversed as explicit reusable/action/entrypoint edges. This is a bounded literal source extractor, not a complete flow-style YAML parser; new nonliteral edges remain review-requiring. All source stays local to the GitHub-hosted job.

**Post-write main audit:** the same GitHub-hosted policy also runs on every `push` to `main`, using immutable `github.event.before` and `github.sha` commits and proving advertised current main is the after-SHA. This is **detective only**: failing CI cannot undo a direct main write. The actual protection/merge controls belong to the open [#922](https://github.com/Zennay/zCloud/issues/922) integration gate, not this PR.

**Monotone fingerprint policy:** each matched dispatch site is hashed from its source line and counted as a multiset; local/remote reusable edges are fingerprinted too. Source paths are included in dispatch fingerprints to distinguish a shared helper from its callers. A new site, duplicate site, changed command or changed dispatch target is rejected—even if the old site was removed so that raw call counts appear equal. An unchanged legacy site may remain while other non-dispatch code changes. Fingerprinting deliberately treats some formatting-only changes to the dispatch line as review-requiring, not as proof of new runtime behavior.

## Trusted policy execution and bootstrap

On later PRs and main pushes, the admission job reads the scanner implementation from **the immutable exact base commit** using `git ls-tree` for regular Git blob mode and `git show BASE:scripts/...py`. It executes this trusted baseline scanner against the new candidate Git object tree. This prevents a candidate PR changing its own checker script to return success while introducing a new dispatch elsewhere. Candidate-source unit tests are still run for code quality, but **not** used as the enforcement authority once a trusted baseline exists.

**Bootstrap limitation:** PR #1502 introduces this file for the first time, so `main` has no baseline checker at present. The job explicitly emits a `BOOTSTRAP ONLY` warning and executes the candidate checker for development feedback. **Green bootstrap CI is not an independently trusted security approval**; an independent reviewer must inspect the guard and its workflow before integrating it. PR-provided workflow source is likewise not an independent trust root for the initial PR. After a reviewed merge, a protected default-branch workflow must become the source of this gate. Main-branch protection remains a separate responsibility under issue #922.

## Read-only acceptance

- `python3 -m unittest -v tests.test_zcloud_scheduled_dispatch_debt_guard_20261016_w31`
- `python3 scripts/zcloud_scheduled_dispatch_debt_guard_20261016_w31.py --base <40-character-main-SHA> --candidate <40-character-PR-head-SHA>`

Outputs contain only repo-relative workflow filenames, bounded counts, Git SHAs and permit/deny status; they never echo workflow content, secrets, command arguments or event payloads. Exit codes: 0 unchanged/no-new-debt; 1 new sites; 2 malformed/incomplete evidence. `mutation_performed=false` and `deploy_authorized=false` always.

Source guard validates SHA syntax, regular blob mode, tree entries, content size, UTF-8, Git object lengths, and rejects control-character/newline/terminal-escape manifest paths. Reusable workflow and nested composite-action dependency traversal is bounded by a visited set (cycles are not followed indefinitely). Git subprocess stdout is **stream-read** through a bounded 64-KiB read loop, rejected immediately above 16 MiB and limited by a 20-second end-to-end deadline. The process is killed on excessive output, timeout or source failure, without exposing its stderr or the source payload.

## Explicit non-claims

This is **not** a complete interpreter for shell variables, opaque/dynamic `uses` expressions (which are conservatively flagged, not resolved), shell scripts imported by workflows or actions, third-party action source, runtime dispatch permissions or indirect external orchestration. It traverses explicitly declared `.github/workflows/*.yml` reusable workflows, `.github/actions/**/action.y(a)ml` manifests and their explicit `main`/`pre`/`post` entrypoints, **not** arbitrary imported scripts, transitively imported JavaScript modules, or external code. In particular, a command assembled through opaque wrappers could escape string-based matching; all privileged production workflows still require separate authorisation.

Passing this PR gate does **not** fix existing [#1216](https://github.com/Zennay/zCloud/issues/1216) redispatch, demonstrate the self-hosted runner is alive, or authorize merging/deploying anything. Actual recovery idempotence has its own [#913](https://github.com/Zennay/zCloud/pull/913) workflow owner and [#1239](https://github.com/Zennay/zCloud/pull/1239) policy owner. Release stays serialized under #580/PWQ-41 + #1089. No manual workflow dispatch, VPS/Firefox/SQLite/worker/runner/queue/service write is part of this source-only guard.
