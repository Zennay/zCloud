# zCloud externe dashboardtriage — operatorgids

Kandidaat bij issue #1166 en PR #1351 (https://github.com/Zennay/zCloud/pull/1351). Alleen observatie. Een groen API-antwoord bewijst geen gezonde productie-deploy, SQLite-write, afgeronde worker-drain of echte AI-generatie. De vastgepinde status-URL gebruikt openbaar HTTP zonder TLS: **een antwoord bewijst ook niet de cryptografisch geverifieerde identiteit van de server**. Machine-uitvoer meldt altijd `transport_authenticated=false`, ook bij status healthy.

## Gebruik — pas NA bevoegde integratie op main

1. Open GitHub Actions, workflow “zCloud external dashboard triage (manual, hosted, read-only)”.
2. Start handmatig op main, door repo-eigenaar Zennay. Er is geen push-, PR-, cron- of healthcheck-trigger.
3. Lees de Nederlandse samenvatting in het Actions-joboverzicht. Maximaal zes GET-pogingen met maximaal 12 seconden per socket-wachttijd, vijf seconden tussen pogingen en **een harde totale procestijd van 115 seconden**. Een traag druppelende HTTP-verbinding mag zo niet eindeloos doorlopen. Vast IP en statuspad, zonder omgevingsproxy of redirect, nooit POST, SSH, sudo, SQLite, Firefox of servicebesturing.
4. Bij fouten: geef bewijs aan de verantwoordelijke #1135 / #580-PWQ-41 / #1089-eigenaar. Geen herstart, repair, SQLite-permissiewijziging, queue-retry of deploy vanuit deze diagnose.

## Uitslagen en betekenis

| Bericht | Interpretatie |
| --- | --- |
| API bereikbaar | Alleen een geldig, vers extern API-antwoord; niet complete productiegezondheid. |
| Hersteld na hercontrole | Tijdelijk transportprobleem gevolgd door een goed antwoord. |
| Verbinding geweigerd/verbroken | TCP-transportfout; geen bewijs dat de runner kapot is. |
| DNS, TLS of time-out | Externe verbinding kon niet binnen budget worden geverifieerd. |
| Onverwachte HTTP-doorverwijzing (3xx) | Niet volgen: kan naar onbedoelde hosts of inlogpagina's verwijzen. |
| HTTP-aanvraag geweigerd (4xx) | Clientzijde, bv. autorisatie/rate-limit; geen VPS-herstart afleiden. |
| HTTP-serverfout (5xx) | Backend geeft foutstatus; vereist onafhankelijke service-evidence. |
| HTTP-status niet 200 (overig) | Ook onbekende/niet-standaard statussen zijn nooit een gezonde API; geen responsebody of secrets loggen. |
| Onverwacht antwoordtype of te groot | Alleen `application/json` met afwezige of ondubbelzinnige UTF-8-charset is geldig. Tegenstrijdige, niet-ASCII, te lange, dubbele of control-character media-parameters worden geweigerd; responses boven het 128 KiB-budget eveneens. Een afwijzing bewijst geen runnerstoring. |
| Tegenstrijdige HTTP-headers | Dubbele content-/transferheaders, opgegeven lengte die niet klopt, ongeldige lengte, lege, control-character-bevattende of anderszins ongeldige Content-Encoding (alleen eenduidige `identity` is toegestaan) of een aanwezige Transfer-Encoding (óók `chunked` of `identity`). HTTP-framing kan dubbelzinnig zijn wanneer bibliotheken transfercodering verwerken: liever onterecht rood dan vals groen. Ook met HTTP 200 geen geldige status. |
| Ongeldige JSON of schema | Body onbruikbaar, vereiste velden ontbreken, of `projects` bevat onbruikbare rijen (bv. null, getallen, strings of geneste arrays in plaats van objecten). Ook een vers HTTP 200-antwoord is dan niet geldig. |
| HTTP-antwoord heeft cacheleeftijd | Een positieve `Age` of een expliciete cache-hit (`hit` / `hit=?1`) geldt als cachebewijs, niet als actuele origin-bereikbaarheid. Ook een `Cache-Status`-cachepad met `fwd-status=304` (revalidatie) of `206` (gedeeltelijke next-hop-response) is geen bewijs van een vers, volledig origineel dashboardantwoord. Malforme identifiers, dubbele parameters, tegenstrijdige `hit`/`fwd` en ongeldige `ttl`/`stored`/`collapsed`/`fwd-status` worden geweigerd. De herkomst blijft bij openbaar HTTP ongeauthenticeerd. |
| Verouderd of toekomstige tijd | >180 seconden oud of >30 seconden in de toekomst: mogelijk cache, replay of klokafwijking. |
| MAIN_CHANGED / MAIN_UNVERIFIABLE | Exacte actuele main-head vóór/na observatie niet bewezen; geen groene samenvatting publiceren. |
| Totale tijdslimiet overschreden | De 115-secondenlimiet stopte een trage externe probe. Eventuele gedeeltelijke response wordt weggegooid; de job blijft fout. |

De manual job verifieert current-main driemaal via **GitHub REST / GitHub CLI** (uitsluitend GET): vóór het externe verzoek, na de externe observatie en **nogmaals na volledige rapportvalidatie, onmiddellijk vóór publicatie**. Elke GET heeft een maximum van 12 seconden; bij verplaatsing, ongeldig of onbereikbaar main volgt geen publicatie. Hij gebruikt alleen het kortlevende GitHub Actions-token met `contents: read`, zodat ook een privérepository werkt; dit token wordt niet geprint of door checkout opgeslagen. Het afzonderlijke dashboard-GET-proces draait met een **volledig opgeschoonde subprocessomgeving** (`env -i`) waarin uitsluitend een **vaste systeempadwaarde** `PATH=/usr/local/bin:/usr/bin:/bin`, `LANG=C.UTF-8` en `TZ=UTC` expliciet toegestaan zijn. Ook een eventueel uit eerdere stappen geërfde PATH-wijziging wordt dus niet doorgegeven. Zo kunnen ook onverwachte of toekomstige omgevingsgeheimen niet worden geërfd; het GitHub API-token blijft uitsluitend beschikbaar tijdens de gescheiden, read-only main-SHA-controle. Een echte subprocess-regressie bewijst deze allowlist met nepcredentials en een willekeurig servicegeheim. Geen werkelijke credentials of HTTP-responsebody verschijnen in het rapport. De query is vast: `repos/Zennay/zCloud/git/ref/heads/main`, met `GH_HOST=github.com` geforceerd en niet-interactieve prompts uitgeschakeld; geen writes, `workflow_run` of automatische dispatch. Pas als alle drie resultaten exact gelijk zijn aan de GitHub event-SHA **én de samenvatting maximaal 2 KiB bedraagt en volledig overeenkomt met de canonieke Nederlandse opmaak**, wordt de menselijke samenvatting gepubliceerd. Een afzonderlijke offline validator (`scripts/zcloud_dashboard_summary_guard_20261014_w1.py`) reconstrueert de volledige tekst uit uitsluitend toegestane statussen, 1–6 pogingen en bekende foutcategorieën. Hij verifieert onder meer dat alle aantallen optellen, hercontrole alleen na daadwerkelijke retries wordt vermeld, de exitcode exact bij het resultaat past en beide veiligheidsteksten ongewijzigd aanwezig zijn. Extra regels, Markdown-injecties, dubbele categorieën, tegenstrijdige claimregels, ongebruikelijke tekencodering en geheime responsegegevens worden afgewezen zonder de verdachte invoer af te drukken. Een exitcode 124 na de hard timeout krijgt uitsluitend een exact vastgestelde foutmelding; nooit ruwe gedeeltelijke output. De validator doet geen netwerkoproep en heeft geen herstelbevoegdheden. Dit voorkomt een deel van de branch-races maar is geen atomaire branch- of live-worker-proof.

## Veilig publicatiecontract

De workflow schrijft de externe observatie eerst naar een tijdelijk bestand en publiceert **uitsluitend de apart gevalideerde uitvoer**. Daarna voegt hij onafhankelijk een vertrouwde `Getoetste main-commit` (volledige 40-hex SHA uit het driemaal gecontroleerde GitHub-event) toe; de externe server of rapporttekst kan dit veld niet aanleveren of overschrijven. Dit helpt operators het bewijs aan de daadwerkelijk uitgevoerde bronversie te koppelen, zonder een atomaire main-lock of echte productiedoorloop te suggereren. De validator faalt met een vaste foutcode wanneer het rapport niet volledig en eenduidig te reconstrueren is; het tijdelijke bronbestand wordt niet gelogd. De offline regressies gebruiken de echte validator vanuit een nagemaakte GitHub Actions-shell, met een nep-GitHub-CLI en zonder echte endpointverbinding. Zowel gewone API-uitslagen als de vaste globale time-outmelding vallen onder deze controle. Een succesvolle publicatie betekent nog steeds alleen dat een *niet cryptografisch geauthenticeerd* HTTP-antwoord bruikbaar geclassificeerd is, nooit dat productieherstel mag beginnen.

## Verificatie zonder production mutation

- PR-CI checkt de onveranderlijke head-commit rechtstreeks, niet de synthetische PR-merge. Een andere repository als PR-bron wordt geweigerd. Beide eigen hosted-only workflows gebruiken `actions/checkout` gepind op exact commit `11bd71901bbe5b1630ceea73d27597364c9af683` (v4.2.2) in plaats van een verplaatsbare `@v4`-tag; `persist-credentials: false` blijft van kracht. De PR-regressie bewaakt die twee SHA-pins.
- Negatieve tests gebruiken tevens een echte tijdelijke 127.0.0.1 HTTP-server, inclusief redirects, 503, foutieve body, oversize, stale snapshot, proxy-injectie en `Content-Length` + `Transfer-Encoding` conflicten (waaronder dubbele transferheaders). Geen productie-GET in de PR-tests.
- De vaste API GET zet `Cache-Control: no-cache, no-store, max-age=0` en `Pragma: no-cache`. Dat zijn verzoeken aan caches, **geen garantie**. Het antwoord wordt daarom bovendien geweigerd als `Age` een positieve leeftijd toont. Een malforme of dubbele `Age`- of `Cache-Status`-header levert een ongeldige-headeruitkomst op; bij `Cache-Status` wordt de gestructureerde boolean `hit` / `hit=?1` als cachehit geweigerd, terwijl `hit=?0`, een echte miss (`fwd=miss`) en tekst in geciteerde `detail`-velden geen hit claimen. Dubbele of tegenstrijdige `hit`/`fwd`-parameters worden eveneens geweigerd (RFC 9211): ook een expliciete `hit=?0` mag niet tegelijk met `fwd` op dezelfde cache staan. Een `fwd`-reden moet een ondubbelzinnige RFC 8941-tokenwaarde zijn, niet een geciteerd veld of boolean. De vaste UTC-tijdstempelcontrole blijft verplicht. De syntaxisregels volgen [RFC 9211](https://www.rfc-editor.org/rfc/rfc9211) en een conservatieve subset van RFC 8941 Structured Fields: cache-identifiers, parameterkeys, onbekende extensiewaarden, begrensde getallen, quotes/escapes en dubbele keys worden gecontroleerd. Onduidelijke en niet-ondersteunde geavanceerde syntaxis wordt afgewezen in plaats van stilzwijgend als vers te worden geïnterpreteerd. Zelfs een HTTP 200 met een syntactisch correct cacheantwoord autoriseert nooit een live herstelbesluit. Zelfs een antwoord zonder cache-signalen kan door het ontbreken van TLS niet cryptografisch aan de server worden toegeschreven. De vaste API GET heeft maximaal 128 KiB body-budget, controle van de aangegeven Content-Length (ook vroege oversize-weigering), weigering van dubbele kritische HTTP-headers en onverwachte Content-Encoding, beperkte nested JSON, duplicate-key/Unicode/nonfinite denial, strenge MIME- en UTC-freshnesscontrole.
- De originele dashboard recovery workflow blijft ongewijzigd; de privilegieerde recover-job blijft gedeactiveerd.
- Succesvolle CI is geen herstelsleutel. Productiedeploy en zCloud-workers behoren aan andere geserialiseerde eigenaren.

## Review- en releasegrens

PR blijft draft totdat exact-head gerichte en volledige suite plus standaard zCloud smoke groen zijn, actuele PR en PR-loze ownership opnieuw gecontroleerd is, en onafhankelijke review plaatsvindt. Dit document autoriseert geen merge, dispatch, runner/job-annulering of productie-VPS-mutatie.
