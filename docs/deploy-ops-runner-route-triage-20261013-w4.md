# zCloud deploy-ops — runner route triage (#1326)

A GitHub Actions job queued with `runner_id: 0` is **not proof** that the VPS listener is offline. The runner may be busy, labels may not match, repository access may be missing, or the job may not be assigned despite an available runner.

## Safe standalone diagnostic

```bash
python3 scripts/zcloud_runner_route_triage_20261013.py --fixture snapshot.json
# Real GitHub read-only GET calls (requires a token authorized for Actions and repository runners):
GITHUB_TOKEN=... python3 scripts/zcloud_runner_route_triage_20261013.py --live
# Read-only least-privilege job inspection without runner inventory/admin access:
GITHUB_TOKEN=... python3 scripts/zcloud_runner_route_triage_20261013.py --jobs-only
```

The offline snapshot object must contain `repository` (`Zennay/zCloud`), UTC `captured_at`, GitHub API `runners` and `queued_runs` arrays, plus `jobs_by_run` keyed by decimal run ID. `--fixture` never touches GitHub or the VPS. `--live` calls only `GET /actions/runners`, `GET /actions/runs?status=queued|in_progress|waiting|pending|requested`, and `GET /actions/runs/{id}/jobs`, with bounded pages, payload sizes and timeouts. A token unable to read runners returns *unknown* in `--live`, never an inferred offline status. The explicit `--jobs-only` mode avoids the runner-registration endpoint entirely; it may classify queued job evidence but always returns `runner_inventory_verified=false` and never concludes that a listener is offline, reachable or eligible. It does not bypass missing queue/job evidence: stale queued runs with zero jobs still return exit 2 (`unknown_incomplete_evidence`). Unlike an all-or-nothing exception, that response now retains safe aggregate `stale_unassigned_jobs` and `unknown_stale_queued_runs` counts, without IDs, prompts or runner authorization.

The live adapter scans all five eligible run states because a hosted preflight can already be `in_progress` while a downstream VPS job remains queued. A queued job is considered stale by its own `created_at`, not by the parent workflow's creation time; otherwise an old preflight produces a false alarm. Missing/contradictory job clocks, cross-filter run races, unpaired Unicode, exponent-overflow JSON and redirected API requests fail closed. API requests explicitly ignore inherited HTTP proxy configuration.

The runner roster is fetched twice (before/after the job observations) and only identical runner ID, online/busy state, and label sets are accepted. Collection taking more than 45 seconds is marked unknown. This only detects visible changes across two readings, not an atomic snapshot or an A→B→A transition; it never authorizes a service restart. The host resource gate must be checked separately.

The emitted JSON contains only aggregate counts and a coarse classification, not issue bodies, workflow log text, GitHub token, private job payload, tab URL or prompt. Codes: **0** = no old unassigned self-hosted jobs observed; **1** = stale unassigned jobs found; **2** = incomplete/invalid evidence (deny). This is *not* a runner-health guarantee or deploy readiness.

Seven runs (IDs `38444164413`, `38417002886`, `38410397682`, `38322965986`, `38322810810`, `38322602441`, `38320348950`) each have a queued job with `runner_id=0` and required labels `[self-hosted, ftmo-research]`. Such missing job evidence is now `unknown_incomplete_evidence`, never a green drained queue; a new run with zero jobs may still be bootstrapping.

This does **not** establish an offline listener: the `ftmo-research` runner may be repository-scoped to FTMO, or a group/label route might deny zCloud, while zCloud's `[self-hosted,zcloud,vps]` runner has separately completed work earlier. Direct runner inventory `/actions/runners` was **not accessible through the connected read-only GitHub fetch surface**, so runner membership, permissions and current busy/offline state remain unverified. Operator with appropriate permissions must reconcile against runner registration, group access and live host evidence. Do not cancel the five zero-job runs or retry dispatch automatically.

The CLI also has a least-privilege `--jobs-only` admission that reads only Actions workflow-run/job GET collections. It is explicitly a degraded observation, not a substitute for runner registration/group entitlement checks. Mixed healthy/unknown evidence is never a green exit: a stale workflow with zero jobs forces classification `unknown_incomplete_evidence` and exit 2 even if other jobs are provably stale; both aggregate counts remain inspectable. The CLI refuses ambiguous historical queued runs with zero job evidence and treats impossible/missing pagination `total_count` values as invalid, including count changes between pages. Read-only GET observations are non-atomic and do not authorize mutations.


## Corrected real GitHub job schema: runner-group sentinel

The first hosted GET-only [run #38462819886](https://github.com/Zennay/zCloud/actions/runs/38462819886) proved that the software tests passed (**118 focused, 806 complete**) but the live witness returned fail-closed with the safe exact error code `invalid_runner_group`. Separate direct GitHub REST reads of queued jobs in `38444164413`, `38417002886` and `38322965986` confirmed the **actual API uses `runner_group_id:0` and `runner_group_name:""`** on unassigned jobs, alongside `runner_id:0`. These are zero/blank **unassigned group sentinels**, not positive runner-group entitlement and not malformed evidence. The triage validator was corrected to permit these values while still rejecting booleans/negative IDs and treating a positive group binding as unverified. Dedicated offline and real localhost HTTP regressions were added.

The real queue's seven currently known unassigned jobs require `self-hosted,ftmo-research`; five old queued `workflow_run` events have no job rows. A successful hosted read still must classify five stale zero-job events as **unknown**; it can now safely retain the seven `ftmo_research` profile counts rather than returning an early schema exception. This does **not** resolve repository/group assignment, prove zCloud's VPS listener is offline or authorize restart/cancel.

## GitHub-hosted live read-only witness (new independent deployment-free action)

The branch-only hosted workflow requests just `contents:read` and `actions:read` using the ephemeral `github.token`; checkout discards stored credentials. The hosted `ubuntu-latest` job runs the focused regressions, calls `--jobs-only` to read the **real zCloud GitHub Actions queue**, feeds the result to `scripts/zcloud_runner_route_receipt_20261013.py`, then runs the complete Python regression suite. The witness never calls runner registration APIs, privileged workflows, VPS, Firefox, SQLite or zCloud worker endpoints.

A jobs-only CLI exit `0` or `1` means the inspected queue snapshot had no unprovable stale jobs; it **does not approve recovery**. An exit `2` means the snapshot is unavailable, raced, outdated or partial. Bash explicitly disables `errexit` around the read-only CLI call to capture expected exit `1/2` and restores `-euo pipefail` before the sanitizer. The sanitizer prints only a bounded fixed-field receipt, refuses any mutation-authority flag, and allows **only explicit fixed diagnostic error codes** to reach GitHub-hosted logs. Invalid receipts fail the job. An incomplete read can pass the hosted software-test job as a visibly **unknown operational observation**, never as a green production gate.

The receipt includes a fixed `stale_label_profiles` histogram: `ftmo_research`, `zcloud_vps`, `other`. No arbitrary runner label, workflow name, job name, GitHub token or raw API reason is emitted. `runner_inventory_verified=false` in this mode. A contradictory sum of histogram counts and `stale_unassigned_jobs` is rejected. The safe `probe_error_code` is emitted only for a fixed code from the source; all other reason contents are suppressed. The `incompleteness_cause` is descriptive, never deployment authority.

Initial hosted [#38462101734](https://github.com/Zennay/zCloud/actions/runs/38462101734) ran a real read-only witness successfully but returned `unknown_incomplete_evidence` without confirmed job counts. Later runs add a controlled error-code field to disambiguate API permission/network failure, cross-query races and other invalid evidence. Consult **that run's exact SHA and final status** before comparing observations. A source CI `SUCCESS` cannot be interpreted as healthy `ftmo-research` runners or ChatGPT generation.
